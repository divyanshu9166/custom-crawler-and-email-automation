# Actual Reacher backend on Windows

**Latest application verification: 537 passing tests.** The [new live acquisition run](LIVE_ACQUISITION_CURRENT.md) now includes one real safe/non-catch-all provider verdict, four unsent drafts and a local FAQ prototype. The original native build and isolated catch-all check below remain historical evidence for the unchanged backend. Broader accuracy, production identity and deployment acceptance remain unproven; no outreach was sent.

The Windows development machine has no Docker or usable WSL distribution. A native build route now uses the same pinned MIT Reacher revision as the Linux Docker build: `681791d3d9a854dfcaadb5eb13e5a2f3cb4eed67` ([upstream v0.11.9 release](https://github.com/reacherhq/check-if-email-exists/releases/tag/v0.11.9)). This is the actual upstream HTTP backend with one exact Windows compatibility guard in its optional RabbitMQ worker. The mailbox-checking core is unchanged. See [the small source patch](../deploy/reacher-windows.patch).

The helper downloads checksum-pinned Rustup 1.29.1, Winlibs GCC and a Strawberry Perl portable archive only when preparation is requested. Only that archive’s native OpenSSL 3.6.1 headers/import libraries and DLLs are extracted for the SDK; the incomplete Git Perl is not used for a vendored OpenSSL build. Rust, caches, source, logs and build provenance stay under `data/tools/reacher-native`. Native compilation outputs use a project-specific space-free build directory under `%LOCALAPPDATA%/OutreachWorkbench`. When a workspace path contains spaces, the PowerShell wrapper creates a project-specific junction under `%LOCALAPPDATA%/OutreachWorkbench` and keeps isolated compiler and OpenSSL SDK files there. GCC resolves junctions internally, so the compiler's physical directory must also have no spaces. Existing unrelated aliases are not replaced. System PATH, Windows features, Apache on port 8080, private app settings and sending controls are not changed.

```powershell
# Initial preparation and real compilation; needs Git for Windows and free disk.
.\scripts\start_native_reacher.ps1 -Prepare -Build

# Start an already-built backend after its hash/provenance check.
.\scripts\start_native_reacher.ps1
```

Build prerequisites are large and initial compilation can take several minutes. The helper uses one compilation worker and a development release build with optimization level 1. The native development build links the pinned portable archive’s OpenSSL 3.6.1 dynamically with `OPENSSL_NO_VENDOR=1`. Rust dependencies remain locked; only the documented optional-worker reactor guard differs from upstream. The existing production Linux Dockerfile uses upstream release defaults and vendored OpenSSL. Native preparation requires at least 8 GiB free disk; this disk check does not establish VPS resource acceptance.

Startup binds only `127.0.0.1:8081`, requires the existing private `REACHER_SECRET`, disables worker mode and clears inherited Reacher storage/webhook/Sentry overrides. The build applies CMake’s documented [`CMAKE_POLICY_VERSION_MINIMUM=3.5`](https://cmake.org/cmake/help/latest/envvar/CMAKE_POLICY_VERSION_MINIMUM.html) compatibility setting without patching dependency source. Readiness submits only an invalid-syntax address, then checks that an incorrect header secret is rejected. Build checksum, source commit, PID and the limited readiness scope are saved without secret values. The helper refuses startup after a changed source or binary. Its thirteen executed regression cases cover tool checksums, archive traversal/symlinks, source/binary provenance inherited runtime overrides and the exact idempotent Windows patch.
